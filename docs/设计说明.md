# 设计说明

## 为什么是"规则优先"

这个管道的第一版用的是关键词规则，不是模型分类。原因有三个：

1. **快**：一个群里一天几百条消息，规则匹配是毫秒级，模型调用要几百毫秒到几秒。
2. **可解释**：每条消息为什么被判为重要，能直接说出命中了哪几个词，出错了也好改。
3. **零成本**：不用 API key，断网也能跑。

模型不是不用，是放在后面：`classify()` 是一个独立函数，替换成模型调用不影响其他环节，接口已经隔离好了。

## 去重策略

按 `(message_id, 内容哈希)` 做去重。只用 message_id 不够——有的平台重发时 id 会变，但内容一样；只用内容哈希也不够——同一句话不同人在不同群发，不应该被当成重复。两个一起用，能覆盖大部分重复推送的场景。

## 过滤顺序

先过滤再分类：不相关的群和非文本消息越早丢掉，后面的处理越轻。每个被丢掉的消息都会打印原因，方便调整规则。

## 数据落库

SQLite 就够了：单机、无并发压力、一个文件带走。表结构很平，字段是 `message_id / ts / group_name / sender_name / text / keywords / important`，方便后面直接 SQL 查询或导出。

## 已知取舍

- 关键词匹配会漏语义（"这周五之前" vs "本周内"），需要更准就上模型
- 目前只处理文本消息，图片/文件被跳过
- 日报是纯文本，没做排版和图表
